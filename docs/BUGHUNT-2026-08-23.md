# Bug hunt — 2026-08-23 (Tier 1-3 expansion)

Comprehensive review of all code added in the Tier 1-3 expansion batch (modern AD /
ADCS, searchsploit, shell handler, DB/LDAP/RPC/rsync/Mongo adapters, nuclei
auto-tag, auth-aware recrawl, Windows privesc, ranged fingerprint, IMDS creds,
dangling-ADCS detector). Reviewed every new module for correctness, false
positives, injection safety, and planner-loop termination.

## Verified clean (no change needed)

- **Adapter contract**: `test_registered_commands_pass_validator` runs every one of
  the 20 registered adapters' default `build_command` through the Validator — all
  pass (in scope, no shell metacharacters). Confirms the new `mongodb://`, `ldap://`,
  `rsync://` URI targets extract correctly for scope, and the mongosh `--eval`
  string carries no forbidden character.
- **Planner termination**: every new ENUM adapter is guarded by `has_action(tool,
  key)`; the RECON UDP pass by `_udp_scanned` (once per host); nuclei by
  `has_action`. No re-propose loops. `_enabled_templates` while-loop always advances
  `i` (no infinite loop).
- **IMDS credential parse**: `_AWS_SECRET_RE`/`_AWS_KEYID_RE` both require their
  literal label, so random 40-char strings do not become "secrets"; a credential is
  only emitted when both key id and secret are present. No false positives.
- **hashcrack identify**: prefix rules are ordered most-specific-first; NetNTLMv2 /
  Kerberos shape checks precede the hex-length fallback. bcrypt length pinned to 53.

## Fixed

### BUG-1 — ADCS ESC false positive outside the Vulnerabilities section
`adcs.parse_certipy` counted an `ESC<n>` token when `in_vulns OR current_template`
was set. Since `current_template` is set throughout the templates section, an
"ESC1" appearing in a template's *description* (prose) would be misread as a
finding. **Fix**: require `in_vulns` — ESC lines are only meaningful inside a
template's `[!] Vulnerabilities` block (certipy always prints that header first).

### BUG-2 — web-CVE version misattributed from a neighbouring product
`webcve._find_version` searched a fixed 24-char window after the app token, so
`"grafana, apache 2.4.1"` could attach apache's `2.4.1` to grafana and fire (or
suppress) a range-matched CVE incorrectly. **Fix**: stop the window at the first
`,`/`;` and shorten it to 14 chars, so a version is only taken when it sits
immediately after the token (the intended `webapp: <Name> <version>` shape).
`"grafana, apache 2.4.1"` now correctly yields no grafana version.
